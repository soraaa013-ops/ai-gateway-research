# 研究结论

企业内部 AI 网关应把不同来源的模型变成可发现、可授权、可验证的开发服务，减少接入和排障成本，保护共享配额与算力。

## 两类上游的差异

| 维度 | 内部 MaaS | 自部署推理服务 |
| --- | --- | --- |
| 认证 | 可能为 Key、JWT、签名或企业代理认证 | 可能为网络隔离或服务凭证 |
| 资源边界 | 项目、租户、账号或部署的配额 | GPU、并发、KV Cache、队列与副本 |
| 模型标识 | 平台模型名、别名或部署 ID | 权重版本、量化、LoRA、模板和服务名 |
| 故障来源 | 平台网关、配额和下游服务 | 排队、OOM、冷启动、推理进程和网络 |
| 成本 | 平台计费或内部配额 | 算力分摊，不能视为免费 |
| 观测 | 平台暴露的 ID、usage 和指标 | 推理与基础设施指标 |

这些是待盘点的可能差异，不代表某个内部平台的既定实现。

## 通用性分层

管理统一，包括内部身份、项目额度与追踪；接入兼容，保留已有 SDK 协议；能力透明，明确原生支持、转换支持、部分支持和不支持的功能。

官方兼容层也存在语义损失。Anthropic 列出工具严格约束、缓存和消息映射等限制；Google 提醒兼容协议不能覆盖所有原生能力。[Anthropic](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk)、[Google](https://ai.google.dev/gemini-api/docs/partner-integration)

因此建议可转换的能力适配，专有能力保留原生路径，无法支持的参数在严格模式报错。网关不能补齐模型本身不具备的能力。

## 调试优先

默认固定模型和部署，关闭网关答案缓存及跨模型降级，重试显式可见。固定输入和版本只提高可追溯性，不保证逐字复现。自部署还要记录量化、模板、解析器和引擎版本。

稳定服务模式可开启同等能力部署之间的故障切换。跨模型切换必须是明确策略，同时满足权限、数据去向和能力约束。

## 职责边界

网关负责访问、适配、策略、路由、用量和追踪；推理平台负责模型加载、批处理、显存管理和 GPU 调度。网关可利用健康和队列信号做准入，不重复实现推理引擎调度。

vLLM 提供生产指标，可关联运行和排队状态，不能仅凭 HTTP 成功率判断服务健康。[vLLM 指标](https://docs.vllm.ai/en/latest/usage/metrics/)

优先复用网关底座。自研集中于内部认证、模型能力目录、项目管理映射、调试入口和兼容性回归。
