# 可实施功能清单

面向最多约 70–80 名内部用户，使用内部 MaaS 和自部署模型。此清单是后续建设服务的功能基线；“实现”既可以配置开源产品，也可以集成现有系统，不意味着每一项都要自研。

**先以 LiteLLM 开源自托管满足 MVP，再按实测差距补适配器或薄门户。** 管理员代发 Key、维护模型文档和协助查日志可满足首期，不要求先做完整自助平台。

## 使用规则

- P0：MVP 必需；条件 P0：只有实际客户端或组织要求触发才纳入；P1：试点后按反馈补齐；P2：暂不做。
- 每项有稳定 ID、父需求、角色、行为、验收、依赖、实现方式和 POC 对应关系。父需求 F01–F24 对应[需求总览](02-requirements.md)。
- 完整排期数据见 [CSV 功能清单](../templates/feature-backlog.csv)。状态全部为待验证与排期，不能将文档存在当成功能完成。
- 管理员负责上游、权限和运维；开发者使用被授权模型及自己的 Key；服务账号面向 CI 或应用，不能由多人共用个人 Key。
- 实际项目角色可映射到开源产品已有对象或私有台账，不强制实现多层组织树。

## MVP 的完整业务闭环

1. 管理员登记一个内部 MaaS 和一个自部署服务，验证认证和基础协议。
2. 为模型建立固定部署别名及能力卡；给开发者创建有权限范围和额度的内部 Key。
3. 开发者根据文档完成聊天、流式和适用的工具调用；不支持能力明确报错。
4. 触发错误或超额时得到可定位信息；管理员能凭请求 ID 查到部署、配置与尝试。
5. 撤销 Key、停用上游、回滚配置和恢复备份均能通过验收。

首期界面可直接使用开源管理台加内部文档。普通用户无需访问管理员后台；无隔离能力的全量日志页面不能开放给普通用户。

## 上线前必须确定的数值

Key 撤销传播时限、单 Key 和共享上游并发、输入输出上限、超时、预算类型、日志留存、备份周期与恢复目标。数值由真实配额、推理容量和团队可接受停机时间决定；未确定前不能验收对应项。

## 首期不做

完整自助审批门户、多层组织树、充值售卖、GPU 调度器、全协议覆盖、语义缓存、智能选模、MCP 平台、多地域部署。多副本与 SSO 若是公司硬要求则前置，不以用户少为理由取消权限和数据隔离。
