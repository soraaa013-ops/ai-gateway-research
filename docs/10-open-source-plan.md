# 70 至 80 人团队的开源落地方案

建议先直接部署 LiteLLM 开源网关并复用管理台，以配置和少量内部 MaaS 适配构建服务。目标是把服务交付给开发者，软件建设不必从自研网关或门户开始。该建议需真实上游 POC 验证，尚未部署或压测。

## 三种建设方式

| 方案 | 适用条件 | 工作内容 | 当前建议 |
| --- | --- | --- | --- |
| 直接使用开源网关 | 已有协议与认证可接，管理员辅助流程可接受 | 部署、配置、接入文档、限额、监控、备份 | 首选 |
| 开源网关加薄集成 | MaaS 认证特殊或确需内部入口 | 补认证适配、模型说明或小型申请入口，沿用底座 Key 和路由 | 发现明确差距后采用 |
| 完整自研 | 核心协议或治理约束无法通过扩展满足 | 自建数据面、管理面、适配与升级体系 | 当前规模与已知需求不足以支持此选择 |

不应为了用户量不大就共享一个上游 Key；身份与资源隔离仍需要。也不应因为总共 80 人就直接部署多集群。

## LiteLLM 能替代什么

| 需求 | 优先落地方式 | 验证与边界 |
| --- | --- | --- |
| 模型映射和兼容接口 | 原生配置已有供应商或兼容上游 | 自定义地址、模型名及真实扩展参数必须实测 |
| 内部 Key、模型范围、基础限额 | 复用虚拟 Key | 核对目标版本的限制粒度和传播行为 |
| 添加模型、创建 Key、基础用量查看 | 复用管理台 | 管理界面存在不代表所有用户隔离功能免费 |
| 内部项目归属 | Key 元数据加私有项目台账起步 | 不能把客户端可任意提交的字段当授权依据 |
| MaaS 特殊签名或令牌 | 插件或小型内部适配服务 | 按实际认证确定，不提前造通用认证平台 |
| 固定部署调试 | 独立别名、关闭 fallback 和答案缓存、固定参数策略 | 不能仅设置名称，需查实际上游验证 |
| 日志排障 | 已有日志平台，首期管理员协助 | 保留请求 ID；全量日志不向普通用户开放 |
| 自助服务和精细组织治理 | 核实版本后决定 | 有商业版边界，可能购买、集成或延后 |

官方文档提供兼容上游配置、虚拟 Key 和管理台。它们是复用依据，不是本公司所有需求已开箱即用的证明。[兼容上游](https://docs.litellm.ai/docs/providers/openai_compatible)、[虚拟 Key](https://docs.litellm.ai/docs/proxy/virtual_keys)、[管理台](https://docs.litellm.ai/docs/proxy/ui)

## 开源版与企业版边界

LiteLLM 官方企业页将 SSO、部分 RBAC、项目管理及审计等列入企业能力；仓库许可证也区分企业目录和其他内容。不要把产品完整功能列表当成免费开源版承诺。固定候选版本后，逐项记录无需 license、需要 license 或未确认。[企业功能](https://docs.litellm.ai/docs/enterprise)、[许可证](https://github.com/BerriAI/litellm/blob/main/LICENSE)

如果公司强制 SSO，先验证可接受的集成或授权方案。前置登录代理只能控制入口，不自动提供网关内的项目授权、日志隔离和用户审计；禁止通过信任客户端传入的身份头补齐授权。

## 替代候选

| 产品 | 本规模下的定位 | 何时进入第二轮 |
| --- | --- | --- |
| LiteLLM | 首选复用验证对象 | 先测真实 MaaS、自部署和客户端 |
| New API | 发 Key、渠道和用量后台导向的备选 | LiteLLM 的管理体验或所需版本边界不满足 |
| Higress | 已有网关或 Kubernetes 体系时的备选 | 团队可复用现有运维和插件经验 |
| Bifrost | 其他底座备选 | 前述候选出现明确协议或运维缺口 |

New API 官方仓库列出兼容接口、路由、访问控制和用量等方向，但仍需验证实际权限和认证。Higress 无需仅因人数小而排除，也不应为本服务单独引入不熟悉的平台。[New API](https://github.com/QuantumNous/new-api)、[Higress](https://higress.ai/en/docs/ai/scene-guide/multi-proxy/)

先试 LiteLLM，只有必需功能失败且扩展代价不合理时再启动一个备选。先满足业务，不进行无边界横向评测。

## 最小部署拓扑

内部 TLS 入口 → 单实例 LiteLLM → MaaS 与自部署推理服务；LiteLLM 连接 PostgreSQL，复用已有日志、告警和备份设施。管理入口只对管理员开放。

官方快速开始使用 LiteLLM 与 PostgreSQL，可作为简单部署起点。[快速开始](https://docs.litellm.ai/docs/proxy/docker_quick_start)

- 采用容器部署即可；有现成容器平台则复用，不强制新建 Kubernetes。
- Redis 不因人数而默认引入；只有目标版本功能依赖共享限流、缓存或扩副本时再配置并验收。
- 单实例意味着维护及故障可能中断服务，必须确认团队能接受并验证恢复；有连续可用要求时直接改双副本及可靠数据库。
- 备份数据库、配置及恢复所需密钥材料；仅备份数据库可能不能恢复加密凭证。
- 固定镜像版本，私有配置存放真实地址与凭证引用；公开仓库不包含生产配置。

## 容量估算方法

总用户数不是并发。先估算忙时请求率、平均请求时长和每个用户同时运行的 Agent 或批处理数，再以真实请求压测。

在稳定负载下，可用“平均在途请求数约等于每秒到达数乘平均处理秒数”做初步估算。例如 20 个活跃用户各每分钟一次请求，平均 30 秒，则平均约 10 个在途请求。这只是算例，不是该团队的容量测量，也不覆盖突发。

先测 5、10、20 个同时在途请求及长上下文场景，逐档观察；这些是试验档位，不是容量承诺。单独评估网关连接/内存、数据库写入、MaaS 配额和推理队列。发现瓶颈再调整网关资源或上游容量，网关扩容不会增加 GPU 或 MaaS 额度。

## 采用或放弃的判断

采用：实际认证可接入、核心协议/工具通过、Key 授权有效、过载受控、请求可排障、备份可恢复，且运维与授权成本可接受。

补薄集成：仅缺内部认证、目录展示或申请入口，能保持上游网关升级能力。

转向备选：核心功能在可用版本中不可获得，或每次升级都需改动大量网关内部代码。比较软件授权、适配维护和运营人力总成本，不单看是否免费。
